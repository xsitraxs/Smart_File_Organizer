# 🗂️ Умный органайзер файлов

Автоматический скрипт для сортировки файлов по папкам в зависимости от их типа. Экономит время на ручную организацию загрузок и рабочих директорий.

## ✨ Возможности

- **Автоматическая сортировка**: Распределяет файлы по категориям (`images`, `documents`, `torrents` и др.).
- **Безопасный режим (`--dry-run`)**: Показывает, что будет сделано, без реального перемещения файлов.
- **Защита от дубликатов**: Три стратегии обработки:
  - `rename` — автоматически переименовывает (добавляет `_1`, `_2` и т.д.)
  - `skip` — пропускает файл при конфликте имён
  - `replace` — заменяет существующий файл, **сохраняя старый как `имя.bak-ГГГГММДД_ЧЧММСС`** (обратимо)
- **Дубликаты по содержимому** (`content_duplicates`, по умолчанию выключено): файл, содержимое которого (SHA-256) уже есть в категории, не переносится — ловит один и тот же файл под разными именами, в том числе внутри одной партии.
- **Отмена операций**: Ведётся журнал всех перемещений (`.organizer_undo.json` в формате JSONL), можно отменить последнее действие или несколько (`--undo`, `--undo-count`, `--undo-info`).
- **Безопасная отмена**: если на исходном месте уже есть новый файл пользователя, undo **не перезаписывает его**, а восстанавливает файл под свободным именем (`rename`), пропускает (`skip`) или заменяет (`replace`) — в соответствии с `duplicate_strategy`.
- **Полностью обратимая стратегия `replace`**: заменённый файл сохраняется как `*.bak-<timestamp>`, и полный `--undo` возвращает на место и его, и новый файл.
- **Пересортировка внутри категорий**: файл, лежащий не в своей папке (`videos/photo.jpg`), будет пересортирован в правильную категорию; файл в правильной папке не трогается.
- **Блокировка по папке**: одновременная сортировка *разных* папок работает параллельно; повторный вход в *ту же* папку из мониторинга пропускается.
- **Мониторинг**: Режим постоянного наблюдения за папкой с автоматической сортировкой новых файлов (`--monitor`). Реагирует на создание, переименование/перемещение в папку и дозапись файлов; не трогает ещё скачивающиеся файлы (проверка стабильности размера/mtime).
- **Игнорирование системных файлов**: Не трогает скрытые файлы и сам скрипт.
- **Статистика**: Выводит отчёт о количестве перемещённых файлов, дубликатов и удалённых пустых директорий.
- **Рекурсивная обработка**: Опциональная сортировка файлов во всех вложенных папках с очисткой пустых директорий.

## 🚀 Установка и использование

### Требования

- Python 3.9+
- Для GUI версии: библиотека `tkinter` (обычно встроена в Python, на Linux может потребоваться установка пакета `python3-tk`).
- Для режима мониторинга: опционально `watchdog` — при отсутствии автоматически используется polling-режим.

Установка (опционально, даёт команды `file-organizer` и `file-organizer-gui`):

```bash
pip install -e .            # ядро + CLI
pip install -e ".[watchdog]"  # + мгновенный мониторинг по событиям ФС
pip install -e ".[dev]"       # + pytest, ruff, mypy, coverage
```

Без установки скрипты запускаются напрямую из каталога проекта.

### Консольный запуск (`file_organizer.py`)

1. **Обычный режим** (файлы будут перемещены):
   ```bash
   python3 file_organizer.py /путь/к/папке
   ```
   *Если путь не указан, используется текущая директория.*

2. **Режим просмотра** (без изменений, только план):
   ```bash
   python3 file_organizer.py /путь/к/папке --dry-run
   ```

3. **Тихий режим** (минимум вывода):
   ```bash
   python3 file_organizer.py /путь/к/папке -q
   ```

4. **Без рекурсии** (только файлы в корне папки):
   ```bash
   python3 file_organizer.py /путь/к/папке --no-recursive
   ```

5. **Отмена последней операции**:
   ```bash
   python3 file_organizer.py /путь/к/папке --undo
   ```

6. **Отменить последние N перемещений** (`-1` = все):
   ```bash
   python3 file_organizer.py /путь/к/папке --undo-count 5
   ```

7. **Режим мониторинга** (постоянное наблюдение за новыми файлами):
   ```bash
   python3 file_organizer.py /путь/к/папке --monitor
   ```

8. **Информация о доступных отменах**:
   ```bash
   python3 file_organizer.py /путь/к/папке --undo-info
   ```

9. **Свой файл конфигурации** (вместо `config.json` рядом с модулем):
   ```bash
   python3 file_organizer.py /путь/к/папке --config /путь/к/my-config.json
   ```

Полный список опций: `python3 file_organizer.py --help`

### Графический интерфейс (`file_organizer_gui.py`)

```bash
python3 file_organizer_gui.py
```

**Возможности GUI:**
- **Выбор папки**: Кнопка для удобного выбора директории через проводник.
- **Рекурсивная обработка**: Опция для сортировки файлов во всех вложенных папках.
- **Тестовый режим**: Галочка для запуска без реального перемещения файлов.
- **Мониторинг**: наблюдение за папкой с учётом выбранных опций (рекурсия, dry-run).
- **Логирование**: Окно с подробным отчётом о действиях в реальном времени.
- **Очистка**: Автоматическое удаление пустых папок после перемещения файлов (при рекурсии).
- **Прогресс-бар**: Визуальное отображение прогресса (первая половина — сканирование и фильтрация, вторая — фактические перемещения; 100% только когда все файлы обработаны).
- **Счётчик отмен**: Сколько операций доступно для отмены (`--undo-info` в GUI).

### Примеры

Сортировка файлов в папке «Загрузки»:


Проверка того, что будет сделано в текущей папке:
```bash

```

Отменить последние 3 перемещения:
```bash
python3 file_organizer.py ~/Downloads --undo-count 3
```

Запустить мониторинг папки «Загрузки»:
```bash
python3 file_organizer.py ~/Downloads --monitor
```

## ⚙️ Как это работает

1. Скрипт сканирует файлы в указанной директории (`os.scandir`, stat берётся бесплатно);
   недоступные подпапки учитываются в статистике ошибок, а не игнорируются молча.
2. Определяет тип файла по расширению.
3. Проверяет безопасность путей и целевой папки категории.
4. Создаёт целевую папку (например, `images`), если она не существует.
5. Перемещает файл в целевую папку.
   - При конфликте имён применяется стратегия из конфига (`rename` / `skip` / `replace`).
   - При `replace` старый файл сохраняется как `имя.bak-<timestamp>`.
6. Все перемещения дописываются в журнал `.organizer_undo.json` (JSONL, append-only).
7. После завершения удаляются пустые папки (при рекурсивном режиме).
8. Выводится статистика по завершении.

## 🔄 Отмена операций

Журнал `.organizer_undo.json` лежит в корне отсортированной папки: одна JSON-запись на строку.
Журнал переживает перезапуск программы, устаревший формат (JSON-массив) читается автоматически.

Поведение `--undo-count N`:

| `N` | Результат |
|-----|-----------|
| `-1` | отменить все операции |
| `0` | ничего не делать (безопасный no-op, журнал не портится) |
| `> 0` | отменить последние `N` операций |
| `> количества операций` | отменить всё с предупреждением |
| `< -1` | некорректное значение — no-op с сообщением |

Если на исходном месте уже существует файл (пользователь создал новый), undo **не затирает его молча**: применяется `duplicate_strategy` из конфига. Неудавшиеся операции остаются в журнале для повторной попытки.

## 🛡️ Безопасность

- Скрипт **не удаляет файлы** при сортировке — только перемещает. Стратегия `replace` сохраняет заменяемый файл как резервную копию `*.bak-<timestamp>`.
  - Исключение: удаляются **пустые** папки при рекурсивной очистке (`clean_empty_dirs`).
- Игнорирует сам себя и скрытые файлы (начинающиеся с `.`).
- Игнорирует файлы-«маркеры» незавершённой загрузки (`.crdownload`, `.part`, `.partial`, `.download`, `.tmp`, `.filepart`) в режиме мониторинга.
- Режим `--dry-run` позволяет предварительно убедиться в корректности действий.
- **Защита от Path Traversal**: проверка, что все обрабатываемые пути находятся внутри рабочей директории (включая симлинки).
- **Защита целевой папки**: после создания папки категории проверяется её `resolve()` — симлинк-категория наружу или небезопасное имя категории не позволят увести файлы за пределы папки.
- **Валидация имён категорий**: имя категории обязано соответствовать `^[a-z0-9_-]+$`; `/`, `\`, `..`, абсолютные пути и зарезервированные в Windows имена (`con`, `nul`, `com1`, `lpt1`, …) запрещены.
- **Лимит длины пути**: если итоговый путь превышает лимит ОС (259 символов в Windows, 1024 в macOS), файл не перемещается — в статистику и лог идёт ошибка, данные остаются на месте.
- **Атомарная запись журнала отмены**: перезапись через временный файл + `os.replace` + `fsync` — сбой питания/прерывание не оставит половинчатый журнал.
- **Последовательность undo/organize**: `undo_last_operation` и `organize_files` синхронизированы одним локом, параллельная работа не повреждает журнал.
- **Валидация путей**: запрет на использование `..`, абсолютных путей и symlink вне директории.
- **Защита системных директорий**: корень ФС (`/`), `/root`, `/home`, домашний каталог пользователя и системные директории (`/etc`, `/usr`, `/bin`, …) запрещены как рабочие папки.
- **Защита от DoS**: лимит итераций подбора имени (1000), лимит размера файла (1 GB по умолчанию, настраивается через `max_file_size`).
- **Маскировка путей** в логах для приватности: относительные пути внутри рабочей папки; имя каталога (или `~/…`), а не абсолютный путь.
- **Валидация конфига**: битый или невалидный `config.json` (включая JSON-массив, не-строковые расширения, невалидные стратегии) не роняет программу — используются настройки по умолчанию.

## 🌍 Платформы (Windows / macOS / Linux)

Поведение на разных файловых системах определяется не «догадкой по ОС», а реальной проверкой:

- **Регистр в именах** — при первой сортировке каталога создаётся и сразу удаляется пробный файл, и по нему проверяется, различает ли ФС регистр. Это важно, потому что APFS можно отформатировать как case-sensitive, а Windows умеет включать регистрозависимость для отдельного каталога: догадка по платформе дала бы неверный ответ.
- **Unicode** — имена сравниваются в нормализации NFC. macOS хранит имена в NFD, поэтому `café` из конфига и `café` с диска — это одна и та же запись, и раньше она могла быть молча перезаписана.
- **Журнал отмены** пишется в POSIX-виде (`папка/файл.txt`) и читается на любой ОС — папку можно перенести между Windows и Linux вместе с журналом.
- **Консоль** — вывод устойчив к узким кодировкам: на Windows-консоли (cp1252) кириллица и рамки больше не вызывают `UnicodeEncodeError`, а при перенаправлении в файл/пайп вывод переводится в UTF-8.
- **Защищённые каталоги** сравниваются и в `resolve()`-форме: на macOS `/etc`, `/var` — симлинки в `/private/...`, и без этого защита не срабатывала. Пользовательский temp (`/var/folders/**` на macOS) защищённым не считается.

Что проверено в CI: тесты идут на **ubuntu + windows + macos** (Python 3.9/3.11/3.12). На macOS выполняются все тесты без пропусков, включая сценарии регистронезависимой ФС; на Windows пропускаются только Unix-специфичные проверки (права `chmod`, пути `/etc`, `/private/var`). Что именно выполнялось и что было пропущено, видно в аннотациях соответствующего job'а.

Ограничения, о которых стоит знать:

- Проверка регистра стоит одного `mkstemp`+`unlink` на каталог и кэшируется по каталогу в пределах процесса.
- Лимит длины пути в Windows — 259 символов, даже если в системе включён `LongPathsEnabled`; для более длинных путей файл не перемещается.
- Проверка регистра невозможна для каталога только для чтения — тогда используется платформенная эвристика (Windows/macOS — нечувствительна, Linux — чувствительна).

## ⚙️ Конфигурация

Файл `config.json` рядом с модулем:

```json
{
  "categories": {
    "images":    ["jpg", "png", "..."],
    "documents": ["pdf", "docx", "..."],
    "other":     []
  },
  "settings": {
    "dry_run":            false,
    "recursive":          true,
    "clean_empty_dirs":   true,
    "ignore_hidden":      true,
    "duplicate_strategy": "rename",
    "use_watchdog":       true,
    "content_duplicates": false,
    "max_undo_entries":   1000,
    "backup_retention_days": 0
  }
}
```

Дополнительные настройки (можно добавить в `settings`):

| Ключ | Тип | По умолчанию | Описание |
|------|-----|--------------|----------|
| `dry_run` | bool | `false` | Только план, без перемещений |
| `recursive` | bool | `true` | Обрабатывать подпапки |
| `clean_empty_dirs` | bool | `true` | Удалять пустые папки после сортировки |
| `ignore_hidden` | bool | `true` | Игнорировать файлы с `.` в начале |
| `duplicate_strategy` | str | `"rename"` | `rename` \| `skip` \| `replace` |
| `use_watchdog` | bool | `true` | Использовать watchdog (если установлен); `false` = polling |
| `script_files` | list[str] | список служебных файлов | Имена файлов, которые не сортируются |
| `max_file_size` | int | `1073741824` | Лимит размера файла в байтах |
| `content_duplicates` | bool | `false` | Не переносить файлы, содержимое которых уже есть в категории (см. ниже) |
| `max_undo_entries` | int | `1000` | Сколько последних операций хранить в журнале отмены (`0` = без ограничения) |
| `backup_retention_days` | int | `0` | Удалять бэкапы `*.bak-*` старше N дней (`0` = хранить всегда) |

Невалидный или нечитаемый конфиг (в том числе JSON-массив вместо объекта)
не роняет программу: используются настройки по умолчанию с предупреждением в логе.
Файл `config.json` создаётся автоматически при первом запуске, если его нет.

### ♻ Дубликаты по содержимому

`duplicate_strategy` ловит только одинаковые **имена** (`report.pdf` и `report_1.pdf`). Если один и тот же файл скачан дважды под разными именами, включите `content_duplicates`:

```json
"settings": { "content_duplicates": true }
```

Тогда перед переносом файл сверяется с содержимым целевой категории: если точно такой же файл (по SHA-256) там уже есть — файл остаётся на месте, а в логе и статистике появляется `♻` и счётчик «Дубликаты по содержимому».

Сравнение двухступенчатое, чтобы не читать все файлы целиком: сначала размер и SHA-256 первых 64 КБ, и только при совпадении — полный SHA-256. Дубликат ловится и внутри одной партии: если два одинаковых файла лежат в разных подпапках, перенесётся только первый.

Файлы внутри категории обрабатываются в детерминированном порядке (сортировка по пути), поэтому остаётся предсказуемый экземпляр — первый по сортировке, а не случайный из порядка файловой системы.

Через CLI то же самое делает флаг `--content-duplicates` (он имеет приоритет над конфигом):

```bash
file_organizer.py ~/Downloads --content-duplicates
```

Что стоит знать:

- По умолчанию опция выключена: без неё чтения файлов при сортировке не происходит (только метаданные).
- Пропущенные дубликаты не попадают в журнал отмены — отменять нечего, файл не тронут.
- В `--dry-run` содержимое не читается: план строится по именам.
- Нечитаемые файлы не ломают сортировку — такой файл просто не участвует в сравнении и переносится как обычно.
- Цена опции — чтение файлов: на 200 файлов по 300 КБ это ≈0.06 с (без опции ≈0.02 с, только метаданные).

## 🙈 Исключения: `.organizerignore`

Положите в корень сортируемой папки файл `.organizerignore` — файлы и папки, попавшие
под его шаблоны, не сортируются и не переносятся. Формат как у `.gitignore`:

```
# комментарий — строки, начинающиеся с «#», не разбираются

*.tmp          # по имени на любом уровне вложенности
*.crdownload
docs/*.pdf     # путь от корня сортируемой папки
node_modules/  # каталог и всё внутри — внутрь даже не заходим
build/cache/   # каталог от корня
!keep.tmp      # отрицание: вернуть файл обратно в сортировку
```

Правила и краевые случаи:

- шаблон **без `/`** сравнивается с именем файла или каталога на любом уровне;
  шаблон **с `/`** — с путём от корня сортируемой папки;
- шаблон **с `/` на конце** исключает каталог целиком — его содержимое не сканируется
  вовсе (на `node_modules` и `.venv` это заметно ускоряет обход);
- решает **последнее совпадение**: `*.tmp` + `!keep.tmp` оставит `keep.tmp` в сортировке;
- читается только **корневой** файл правил; `.organizerignore` во вложенной папке
  не используется;
- сам файл правил никогда не сортируется (даже при `ignore_hidden: false`), а
  исключённые каталоги не удаляются при очистке пустых папок — «не трогать» значит не трогать;
- сравнение регистрозависимое, поддерживается BOM и битые байты (они заменяются,
  остальные строки продолжают работать);
- если файла нет — поведение не меняется; если строки нет смысла (каталог с таким
  именем вместо файла) — сортировка продолжается, в логе появляется предупреждение.

В логе видно, что правила применились:

```
  🙈 .organizerignore: файлов пропущено: 2, папок: 1
```

Число поштучно исключённых файлов лежит в статистике как `stats["ignored"]`, а CLI
дописывает строку `Исключено по .organizerignore: N`.

## 🧰 Надёжность и журнал отмены

**Журнал не растёт бесконечно.** Каждая сортировка дописывает записи в `.organizer_undo.json`, поэтому по умолчанию хранятся последние `max_undo_entries` операций (1000). При превышении самые старые записи удаляются — в логе появляется `🗜 Журнал отмены: удалено старых записей: N`, а в статистике есть поле `journal_trimmed`. Отменить можно то, что осталось в журнале; поставьте `0`, если хотите хранить всё.

**Журнал переживает сбои.** Записи добавляются построчно (JSONL) и сбрасываются в ОС сразу, а на диск (fsync) — пачками и в конце сортировки. Оборванная строка после Ctrl+C пропускается при чтении, остальные записи остаются рабочими; полная перезапись журнала (отмена, компактизация, очистка бэкапов) идёт через временный файл, `fsync` и `os.replace` — половинчатого журнала не бывает.

**Бэкапы заменённых файлов убираются.** Стратегия `replace` сохраняет заменённый файл как `<имя>.bak-ГГГГММДД_ЧЧММСС`. Такие файлы не сортируются (остаются рядом с заменённым файлом — иначе undo не нашёл бы их по журналу), а при `backup_retention_days > 0` старые бэкапы удаляются вместе с записями журнала, которые на них ссылаются:

```json
"settings": { "backup_retention_days": 7 }
```

```bash
file_organizer.py ~/Downloads --backup-retention-days 7   # разовая уборка
```

Удаляются только имена строго вида `*.bak-ГГГГММДД_ЧЧММСС` — чужие файлы, лишь похожие на бэкапы, не трогаются. В `--dry-run` уборка только сообщает, что было бы удалено.

**Что остаётся на пользователе.** Если процесс убит в микроконтексте между перемещением файла и записью строки в журнал, эта операция в журнал не попадёт — файл останется в категории, но undo его не увидит. Окно — время одной записи в файл; сами файлы при этом никогда не удаляются, только перемещаются.

## 🧪 Тестирование

```bash
python3 -m unittest test_organizer_core     # без зависимостей
python3 test_organizer_core.py              # то же, через собственный runner
pytest                                       # если установлен pytest
```

Проверки качества кода (dev-зависимости):

```bash
ruff check .
mypy .
coverage run -m unittest test_organizer_core && coverage report -m
```

Тесты запускаются в CI сразу на трёх ОС (см. `.github/workflows/ci.yml`). Сценарии для регистронезависимых ФС в классе `TestRealCaseInsensitiveFS` на Linux честно пропускаются — подделывать флаг нельзя, иначе тест перестаёт проверять то, что заявляет; на macOS и Windows они выполняются по-настоящему.
