## 0. Вердикт

Проект **аккуратно написан, но опасен в эксплуатации**. Видно, что код уже проходил «укрепление безопасности»: есть JSONL-лог отмены, валидация путей, блокировка от параллельных запусков, `os.scandir` вместо `rglob`, 31 тест, mypy strict почти чистый. Но:**найденные дефекты бьют ровно в самые громкие обещания README — безопасность и отмену.**

Три главные проблемы:

1. **Отмена (`--undo`) молча уничтожает файлы.** Проверено: файл, появившийся на исходном месте после сортировки, затирается без предупреждения (POSIX). Это необратимая потеря данных пользователя.

3. **Конфиг и CLI врут пользователю.** Одна опечатка в `config.json` выбрасывает все настройки; `dry_run` невозможно выключить; `--config` не работает; `--undo-info` не печатает ничего, потому что CLI вообще не настраивает логирование.

## 2. 🔴 Critical

### C1. `undo` молча перезаписывает файл пользователя — необратимая потеря данных

**Где:** `organizer_core.py:902` — `shutil.move(str(dest), str(src))`, перед вызовом проверяется только `dest.exists()` (`:894`), существование `src` — нет.

**Сценарий:** пользователь сортирует папку → на исходное место кладётся **новый** файл с тем же именем (свежая версия договора, повторно скачанная фотография) → пользователь вызывает `--undo`. На Linux/macOS `shutil.move` = `os.rename`, а `rename` по спецификации POSIX **атомарно заменяет** цель. Новый файл исчезает, откат рапортует «✓ Восстановлен», лог отмены очищается. Восстановить нечем.

**Доказательство** (`audit/probes/p01_undo_overwrite.py`, вывод `audit/evidence/p01.txt`):

```
1) organize_files: moved=1
   documents/report.txt: ВЕРСИЯ 1 — оригинал
2) пользователь создаёт root/report.txt: "ВЕРСИЯ 2 — новый файл"
3) undo_last_operation: {'restored': 1, 'errors': 0}
   root/report.txt: ВЕРСИЯ 1 — оригинал       ← ВЕРСИЯ 2 ИСЧЕЗЛА
   остаток undo-лога: 0
РЕЗУЛЬТАТ: ❌ ПОТЕРЯ ДАННЫХ — новый файл затёрт без предупреждения
```

На Windows `os.rename` падает с `FileExistsError` → откат не сработает, но и не разрушит (зато пользователь получит «ошибку» вместо восстановления). Поведение платформозависимо, и ни один вариант не является корректным.

**Починка** (минимальная):

```python
if src.exists():
    # не трогать чужой файл: восстановить рядом с суффиксом
    alt = _get_unique_path(src.parent, src.name)
    log(f"  ⚠  Исходное имя занято: {src.name} → {alt.name}")
    src = alt
src.parent.mkdir(parents=True, exist_ok=True)
shutil.move(str(dest), str(src))
```

Плюс: `replace`-стратегия дубликатов (`:722` `target_path.unlink()` до `shutil.move` на `:735`) имеет тот же запах — файл удаляется до того, как исходник гарантированно лёг на место. См. M3.

### C2. «Защита системных директорий» — дырявый чёрный список, а дефолты разрушают структуру папок

**Где:** `organizer_core.py:54-62` (`PROTECTED_ABS_PATHS`), проверка `:596`.

Проверено empirice (`audit/evidence/p12.txt`):

```
  /        protected=False        /etc    protected=True
  /home    protected=False        /usr    protected=True
  /root    protected=False        /var    protected=True
  /tmp     protected=False        /boot   protected=True
  /opt     protected=False        /dev    protected=True
  /srv     protected=False        /proc   protected=True
  /mnt     protected=False        /sys    protected=True
  /media   protected=False
```

То есть защищены «неудобные» системные пути, но **не защищены домашние каталоги пользователей, `/tmp`, `/opt`, `/mnt`, `/media`, `/` — то есть ровно те, где органайзер и применяют**. На macOS не защищён `/Users`, на Windows — `C:\Users`. Запуск `python file_organizer.py ~` или `/` ничем не блокируется.

Усугубляется дефолтами `recursive: true` и `clean_empty_dirs: true` (`organizer_core.py:83-84`). Репро `p12_destructive_defaults.py` показывает итог для типовой рабочей папки:

```
ДО:  Documents/contracts/scan.pdf, Downloads/archive.zip, Music/album/song.mp3,
     Photos/2024/{summer,winter}/img.jpg, Projects/app/{README.md,src}/main.py
ПОСЛЕ: archives/, audio/, code/, documents/, images/ в корне,
       исходные подпапки удалены (empty_dirs_removed=10)
       (папка Documents/ уцелела лишь из-за отдельного бага H6 — её имя совпало с категорией)
```

Ни подтверждения, ни dry-run по умолчанию, ни бэкапа, ни исключений — и всё это на **рабочем** каталоге пользователя.

Отдельная насмешка: в модуле объявлен `PROTECTED_DIRS` (`:47-52`) с `home`, `root`, `tmp`, `bin`… — но он **не используется нигде** (проверяется только `PROTECTED_ABS_PATHS`). Мёртвый код, создающий иллюзию защиты; см. L1.

**Починка:**

```python
PROTECTED_ABS_PATHS = [Path(p) for p in (...)]  + [Path("/"), Path.home(), Path("/Users"), Path("C:\\Users")]
# плюс белый список «безопасных» корней и требование --force для всего остального:
if _is_protected_dir(source_path) or source_path == Path(source_path.anchor) \
        or Path.home() == source_path or Path.home() in source_path.parents:
    raise ValueError("Отказ: путь вне пользовательских данных; используйте --force")
```

Плюс: `clean_empty_dirs` для чужих подпапок должен по умолчанию быть **выключен**, а `recursive` — включаться только явным флагом. `PROTECTED_DIRS` — либо задействовать как второй уровень проверки (по имени, с учётом корня), либо удалить.

### C3. `undo` падает с `KeyError` на первой же неполной записи лога — отмена не выполняется вовсе

**Где:** `organizer_core.py:878-879` — `entry["destination"]` / `entry["source"]` через `[]` (при том что рядом, в `:884`, используется безопасный `.get()`).

`_load_undo_log` считает валидной любую JSON-строку-объект. Достаточно записи без `destination` (обрыв записи при сбое диска, вручную отредактированный лог, лог от другой/старой версии) — и **вся** отмена падает с исключением, не восстановив ни одного файла, включая полностью корректные записи.

**Доказательство** (`p11_undo_log_robustness.py`, `evidence/p11.txt`):

```
get_undo_count: 2 (битая запись считается валидной)
CRASH: KeyError 'destination'
файл восстановлен: False
```

**Починка:** валидировать схему записи в `_load_undo_log` (обязательные ключи `action`, `source`, `destination` типа `str`), битые записи отбрасывать с предупреждением и **не удалять** их из лога, либо обернуть разбор каждой записи в `try/except KeyError` и складывать такие записи в `failed`.

## 3. 🟠 High

### H1. Одна опечатка в `config.json` выбрасывает **весь** пользовательский конфиг

**Где:** `_validate_config_schema` (`:109-141`) возвращает `False` на любую проблему, а `load_config` (`:165-166`) при `False` берёт `DEFAULT_CONFIG` целиком — вместе с `categories`.

**Доказательство** (`evidence/p03…`, отдельный прогон): конфиг с `duplicate_strategy: "rename_typo"` и пользовательской категорией `notes` →

```
WARNING: неверное значение duplicate_strategy='rename_typo'
WARNING: config.json не прошёл валидацию схемы. Используются дефолтные настройки.
категории, которые увидит пользователь: ['documents', 'images', 'other']   ← «notes» потеряна
```

Пользователь правил одну строку — получил молча другие категории и другие настройки. Это не «безопасный фолбэк», это подмена пользовательских данных.

**Починка:** валидировать по-полево. Невалидное поле — заменить только его дефолтом с предупреждением; невалидную категорию — отбросить только её; при фатальной ошибке JSON — сохранить рядом резервную копию (`config.json.bak`) перед использованием дефолтов.

### H2. `max_file_size` строкой («1GB», «500 MB») роняет сортировку `TypeError`-ом

**Где:** `organizer_core.py:580` + `:674`; тип поля не валидируется (`max_file_size` отсутствует в `type_checks`).

```
CRASH: TypeError '>' not supported between instances of 'int' and 'str'
```

Человекочитаемая запись размера — самое естественное, что сделает пользователь после «Лимит размера файла (1GB по умолчанию)» в README. В итоге — не «пропуск больших файлов», а полный отказ сортировки с невнятной ошибкой. **Починка:** парсер `"1GB" | 512 | "10MB"` → байты, либо строгая валидация с понятным сообщением.

### H3. `dry_run: true` в конфиге — ловушка без выхода

**Где:** `organizer_core.py:585` — `use_dry_run = settings.get("dry_run", False) or dry_run` — это **ИЛИ**, а не переопределение аргументом. В GUI (`file_organizer_gui.py:269-270`) `dry_run` только выставляется в `True`, снять его из интерфейса невозможно.

Итог (репро `p08_dry_run_locked.py`): при `settings.dry_run = true` вызов `organize_files(..., dry_run=False)` **не перемещает файлы, но возвращает `moved: 1`**. GUI в этом случае показывает «✅ Готово — перемещено: 1» и диалог с числом перемещённых файлов, а на диске не меняется ровно ничего: шапка «⚠ DRY-RUN» уходит только в лог-панель, которую пользователь не читает. Классический «тихий холостой ход»: пользователь уверен, что файлы отсортированы.

**Починка:** аргумент должен переопределять конфиг (`dry_run if dry_run is not None else settings.get(...)`, как это уже сделано для `recursive`), в GUI — явно передавать `False` при снятой галочке.

### H4. CLI-флаг `--config` принимается и полностью игнорируется

**Где:** `file_organizer.py:71-74` (объявление) и `:87` — `config = load_config()` без пути.

**Доказательство** (`evidence/p03.txt`): запуск с кастомным конфигом, где `txt → notes`, создал папку `documents` и не создал `notes`:

```
exit code: 0 · stdout: '' · созданные папки: ['.organizer_undo.json', 'documents']
РЕЗУЛЬТАТ: ❌ --config полностью игнорируется
```

Флаг не задокументирован в README, но присутствует в `--help` — то есть пользователь на него наткнётся и будет введён в заблуждение. **Починка:** прокинуть путь в `load_config` (сейчас `CONFIG_FILE` — жёстко зашитый `Path(__file__).parent / "config.json"`, `:35`), либо удалить флаг.

### H5. CLI немой: логирование не настроено, `--undo-info` не печатает ничего

**Где:** `file_organizer.py:21` — `logger = logging.getLogger(__name__)`, и нигде нет `logging.basicConfig`. Корневой логгер без обработчиков → `lastResort` показывает только `WARNING+` в stderr.

**Доказательство** (`evidence/p04.txt`):

```
--undo-info  -> rc=0 stdout='' stderr=''          ← команда «показать количество отмен» молчит
сортировка   -> rc=0 stdout=''
                 (весь вывод ушёл в logger.info и был отброшен)
--monitor    -> stdout='' stderr=''                ← и баннер, и события мониторинга невидимы
```

При этом сам `organizer_core` вешает свой `StreamHandler` (`:15-25`) — поэтому при сортировке пользователь видит сырой stderr-поток логов ядра с таймстампами, а собственные сообщения CLI (в том числе «Доступно операций для отмены: N») не видит никогда. Документированная в README команда `--undo-info` — по факту no-op.

**Починка:** `logging.basicConfig(level=..., format=...)` в `main()`; либо перевести CLI на `print`/`log_callback`. Заодно развести «сообщения CLI» и «логи ядра».

### H6. Пользовательские папки `Documents/`, `Photos/`, `Music/` молча не сортируются

**Где:** `_should_skip` (`:632-644`), проверка `:639` — «первый элемент относительного пути (в нижнем регистре) совпадает с именем категории → пропустить».

Задумывалось как «не трогать уже отсортированное». Реально (репро `p13_category_name_heuristic.py`):

```
Documents/contract.pdf отсортирован: False   ← папка пользователя Documents пропущена целиком
Music/track.mp3        отсортирован: True    ← «music» не категория, повезло
my_notes/todo.txt      отсортирован: True
файл "images" (без расширения) пропущен молча, skipped=0
```

На Windows/macOS папка `Documents` (или `Pictures`/`Photos`, `Videos`) в профиле пользователя называется ровно так же, как категория, — и органайзер её просто не видит. Хуже: файл в корне, названный `images`/`code`/`other`, тоже пропускается **и не попадает даже в счётчик `skipped`** — статистика (`skipped: 0`) врёт.

**Починка:** не угадывать по имени, а запоминать/помечать собственные каталоги (например, хранить их список в `.organizer_meta.json` или проверять, что каталог создан самим органайзером), и сравнивать только первый уровень; файлы в корне не сопоставлять с именами категорий.

## 4. 🟡 Medium

### M1. `undo_last_operation(count=0)` отменяет **всё** и плодит дубликаты в логе
`organizer_core.py:867-868`: `all_entries[-0:]` — это весь список; `remaining = all_entries[:len-0]` — тоже весь список. Репро `p02`:

```
undo(count=0) -> {'restored': 3, 'errors': 0}   (ожидалось: не отменять ничего)
undo-лог после отмены count=0: 3                 (ожидалось 0)
после 3 повторных сортировок undo-лог = 6 (файлов всего 3)
```

Лог раздувается, при повторных циклах в нём накапливаются записи об уже отменённых перемещениях (их «отмена» позже даст ошибки `Файл не найден`). Отрицательные `count`, кроме `-1` (например `--undo-count -2`), дают такой же мусор. **Починка:** `if count <= 0: to_undo, remaining = [], all_entries`; валидация `count` в CLI.

### M2. Case-insensitive дедупликация обойдена из основного потока
Защита живёт в `_get_unique_path` (`:326`, `case_insensitive = os.name == "nt"`), но вызывающий код сначала сам решает, дубликат ли это: `:714` — `if file_path.name in existing_names:` (регистрозависимо) — и лишь внутри ветки `rename` зовёт `_get_unique_path`. Спай в репро `p09` подтверждает: **функция не вызывается ни разу**:

```
_get_unique_path с набором {'Report.TXT'} -> report.txt
вызовов _get_unique_path из organize_files: []
в documents/ сейчас: ['Report.TXT', 'report.txt']
```

Последствия: Windows — `FileExistsError` и файл остаётся неотсортированным; macOS (APFS/HFS+ по умолчанию регистронезависимы) — `os.rename` **заменяет** существующий файл, т.е. тихая потеря данных на самой популярной «бытовой» платформе. Последний тест `TestCaseInsensitiveDedup` проверяет `_get_unique_path` в вакууме и байпас не ловит. **Починка:** вынести решение «дубликат» в одну функцию `_resolve_target(existing_names, name, strategy, case_insensitive)` и не дублировать логику в вызывающем коде.

### M3. Стратегия `replace` удаляет существующий файл **до** успешного переноса
`:722` `target_path.unlink()` → `:735` `shutil.move(...)`. Если перенос упадёт (права, занятость, обрыв копирования между ФС), старого файла в категории уже нет, исходник остался лежать где был. Пользователь получает «ошибку» и минус файл. **Починка:** переносить во временное имя (`*.part`) и заменять через `os.replace` только после успеха, либо сначала `copy2` во временный файл, затем атомарная замена и удаление источника.

### M4. `_action_log` растёт без границ — утечка памяти в мониторинге
`:98` + `:772-775`. Данные не читает никто, кроме теста (комментарий это подтверждает), а в долгоживущем процессе мониторинга список копится вечно: репро `p07` — `len(_action_log) = 300` после 300 циклов. **Починка:** удалить переменную вместе с `session_log` (лог отмены и так пишется в JSONL), либо ограничить `deque(maxlen=1000)`.

### M5. Watchdog реагирует на собственные перемещения — лишний проход сортировки
Репро `p05b_watchdog_events.py`: при переносе файла в категорию сам органайзер порождает события `created` (файл в `images/`), `created` (каталог), `deleted` (исходник) — обработчик снова накапливает pending и запускает сортировку (в логе `p05_watchdog.txt` видно «Новых файлов: 2 → Файлов для обработки: 0»). Цикл завершается, но каждый проход порождает лишний. Плюс счётчик `Новых файлов: N` считает **события ФС**, а не файлы, — вводит в заблуждение. **Починка:** игнорировать события внутри управляемых каталогов и собственные перемещения (сравнение `src_path`/`dest_path` с целями).

### M6. `TestConcurrentOrganize` флейковый: 2–3 падения на 80 прогонов (2–4 %)
Репро `p10_flaky_concurrency_test.py 80` → `AssertionError: 2 != 1` в каждом втором-третьем десятке запусков — вызовы, стартовавшие в разные моменты, отрабатывают «законно» по 2–3 раза, а тест требует ровно один. Строка `assertGreaterEqual(len(skipped), 0)` (`test_organizer_core.py:485`) не проверяет ничего (всегда истина). Итог: CI-шум и потеря доверия к зелёной сборке. **Починка:** тест должен фиксировать отсутствие порчи лога/файлов, а не количество «успевших» вызовов; вместо подсчёта — инъекция задержки в `organize_files` (monkeypatch) и детерминированная проверка.

### M7. Симлинки: шум в статистике и ломающиеся ссылки
Репро `p06_symlink_behaviour.py`:

```
stats: errors=1
  ✗ Пропущен небезопасный путь: link_outside.txt
ссылка-на-каталог осталась в корне: False   ← цель ссылки удалена как «пустая»
```

Симлинк на файл вне папки честно блокируется, но пишется как **ошибка** — при каждом запуске счётчик ошибок растёт (пользователь думает, что органайзер сломан). Каталог-цель симлинка опустел и был удалён → ссылка стала битой. README обещает «проверку symlink», не описывая ни одного из этих эффектов. **Починка:** отдельный счётчик `symlinks_skipped`, не трогать каталоги, на которые ссылаются симлинки.

### M8. `.gitignore` обёрнут в маркдаун-забор
Первая и последняя строки файла — ```` ``` ```` (подтверждено `cat -A`). Правила при этом работают (`git check-ignore` корректно матчит `__pycache__/`, `*.log`, `.venv/`), а строка ```` ``` ```` висит мусорным паттерном. ## 8. Что действительно сделано хорошо (без иронии)

- **`_UndoLogWriter` (JSONL, append-only)** — устраняет O(N²) read-modify-write, не блокирует цикл, устойчив к обрыву. Грамотное инженерное решение.
- **Пакетная обработка по категориям** (один `mkdir`/`scandir` на категорию, in-memory проверка коллизий) + `os.scandir` вместо `rglob` — реальный и заметный выигрыш.
- **Защита undo-лога от path traversal** (`_validate_path_safety` для `src` и `dest`, `:883, :888`): абсолютные пути и `..` из подделанного лога отсекаются корректно — проверено чтением кода и существующими тестами.
- **`_organize_lock`** (неблокирующий) — параллельные запуски не портят лог; тест это подтверждает (когда не флейкует).
- **Обратная совместимость форматов undo-лога** (старый JSON-массив + новый JSONL) и терпимость к битым строкам на уровне *загрузки*.
- **31 тест**, среди которых есть внятные сценарии (частичная отмена, стратегии дубликатов, персистентность лога, защита `..`, ложные срабатывания защищённых имён).
- **`load_config` с deep-merge, mtime-кэшем и возвратом `deepcopy`** — аккуратно.
